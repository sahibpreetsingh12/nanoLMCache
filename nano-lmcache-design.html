nano-lmcache

Design & build plan · a finishable end-to-end KV cache, written from scratch · Mac, CPU-only, no GPU

The goal

Build the whole pipeline — prompt → tokens → chunks → KV in L0 → store to L1 → evict → demote to L2 — in roughly 700 lines of my own code. Not a clone of LMCache, not a toy that only proves what I already believe: every stage ends in something that runs and something that can fail.

1The tier hierarchy (correcting my own mental model)

I had this inverted — was thinking “hot cache → cold cache → evicts to L1 storage.” It is the other way round, and there are three tiers, not two.

TierWhat it isTemperature
L0 The engine's own KV cache — the paged pool in GPU HBM (plain RAM in my setup) hottest
L1 LMCache's in-daemon memory slab — sized by --l1-size-gb hot
L2 Backing adapters — local disk, remote store cold

L1 is the hot cache. Eviction moves data down and out of L1 — either to L2 or discarded entirely.

This is why every Aug 28 log line read 2 L1, 0 L2: two chunks found in hot memory, none in cold storage, because no L2 was configured. The --enable-extra-logging flag confirms the direction — it reports “L0↔L1 store/retrieve throughput.” L0 is where data comes from.

3Why the data path is the interesting part

Chunking, the thing I read about for weeks, is ten lines (token_database.py:347–365):

end = len(tokens) if save_unfull_chunk else (len(tokens) - len(tokens) % self.chunk_size)
for i in range(0, end, self.chunk_size):
    yield tokens[i : i + self.chunk_size]

prefix_hash = self._get_init_hash()
for token_chunk in token_chunks:
    prefix_hash = self._hash_tokens(token_chunk, prefix_hash)   # <- chained
    yield prefix_hash

That retroactively explains Aug 28: 641 tokens → 2 chunks, 129 discarded is save_unfull_chunk=False truncating end to a multiple of chunk_size. Prefix-based reuse is the hash being chained — chunk N's key is hash(chunk_N, hash_of_everything_before). Same prefix → same keys. That is the whole 2/3-chunks-hit result, in one line of code.

The real question: how does data leave the KV cache?

The engine does not store KV contiguously. It is a paged pool — one big tensor carved into fixed-size blocks:

KV pool:  [num_layers, 2, num_blocks, block_size, num_kv_heads, head_dim]
                        ↑                ↑
                    K and V         e.g. 16 tokens per block

A request gets a block table — a list of block IDs, scattered wherever there was room:

request tokens:  [0 ...................................... 255]   one 256-token chunk
block table:     [ 47 ][ 3 ][ 91 ][ 12 ][ 88 ][ 5 ] ...  16 blocks, non-contiguous
physical pool:   ...  #3  ...  #5  ...  #12  ...  #47  ...  #88  ...  #91  ...

So one LMCache chunk (256 tokens) spans 16 engine blocks (16 tokens each), scattered across the pool, in every layer. Which makes the two operations obvious:

  • Store = gather. Walk the block table, pull 16 scattered blocks per layer, lay them out contiguously in one buffer, hand it over.
  • Retrieve = scatter. The new request has different block IDs — the pool moved on. Take the contiguous buffer and write it back into wherever this request's blocks actually are.
That is EngineDrivenTransferContext — “worker gathers its scattered paged KV blocks into one buffer.” The sentence from the Aug 28 table becomes a loop with index arithmetic.

5Build order — every stage ends in something that runs

Stage 1 · Tokens and keys

tokenizer.py + token_db.py. Feed it a prompt, print the chunks and their chained hashes. Then feed it a second prompt sharing a prefix and watch the first N hashes come out identical. ~30 minutes, and prefix-based reuse stops being a claim I read somewhere.

Stage 2 · The data path

engine.py + transfer.py. Build a scattered block table, gather to a flat buffer, scatter into different blocks, assert equality. If the indexing is off by a block, a layer or a head, it fails — this is the forcing function.

Stage 3 · A real cache hit

l1.py + cache.py. Same prompt twice: miss, then hit. This is the 4.3× moment, in code I wrote. Probably the stage I am actually chasing.

Stage 4 · Eviction

eviction.py + controller.py. Tiny L1, push distinct prompts, watch the watermark trip and LRU choose victims. Replaces Stages 0–3 of the experiment plan — reading my own log lines instead of the daemon's.

Stage 5 · The cold tier

l2.py. Evict to disk instead of discarding, then hit a promoted chunk on the way back up. 0 L2 finally becomes non-zero.

6Scope boundary

Explicitly out: real model weights · GPU / CUDA · attention · the two-process split · ZMQ / shared memory · compression · IsolatedLRU and cache_salt · distributed anything · CacheBlend.

On the process split. It is a core LMCache principle, but doing it now means drowning in ZMQ before there is a cache to talk to. Build single-process with a clean seam: l1.py never imports engine.py; they communicate only through explicit buffers and keys. Then the split is an optional Stage 6, not a rewrite.

7The rule that keeps this honest

Every stage needs an assertion that can fail.

A toy written from scratch will happily encode my misconceptions and run green forever — building a mirror and calling it a microscope. The defence is that reality gets a vote at each stage:

  • Stage 2 — round-trip equality after gather/scatter. Has one naturally.
  • Stage 3 — verify retrieved KV equals what was stored.
  • Stage 4 — predict which key dies before running, then check.
  • Stage 5 — a chunk demoted to disk and promoted back must be byte-identical.
Everything genuinely learned this year came from being contradicted: NO_CUDA_EXT did not mean skip-CUDA; the venv rename was not harmless; the patch was not fine. Keep that mechanism alive here on purpose.

8Open decision

Real tokenizer or toy? Leaning real — facebook/opt-125m's tokenizer is already downloaded, it is a few MB, and real tokenization reproduces the messy word-count ≠ token-count behaviour that cost a calibration detour on Aug 28. A toy tokenizer hides exactly that.

Then pick small, printable dimensions for the fake pool — num_layers, block_size, num_kv_heads, head_dim — numbers that can be eyeballed in a terminal, not realistic ones.
